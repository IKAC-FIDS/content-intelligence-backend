# Fix 000087 PostgreSQL RLS operations and security model

## Scope and identity model

RLS is a second isolation layer; the explicit application `organizationId`
predicates from fix 000085 remain mandatory. The first canary is only
`notifications`. It has a required direct `organizationId`, no unresolved rows
on the representative restore, a dedicated organization index and a composite
hot-list index. It provides representative list/count/create/update/delete and
background-job coverage with a bounded query surface.

`Company`, `Opportunity`, `Task`, `Meeting`, `Team`, `User`,
`OrganizationMembership`, `Organization`, `Attachment`, `AuditLog`, and all
indirectly owned/global tables are deferred. The first four have broad reports,
nested services or jobs that still need transaction-client propagation. Team is
read during authentication and authorization. User, Membership and Organization
are Tenant-resolution bootstrap dependencies. Attachment has external MinIO
side effects. AuditLog may be platform-wide and nullable. Indirect and global
tables require separate ownership decisions. This fix does not claim database-
wide RLS.

The database identities are deliberately separate:

- `MIGRATION_DATABASE_URL`: schema/table owner used only for migrations,
  validated maintenance and full backup/restore. It may bypass RLS because it is
  the owner/superuser in current local Compose environments.
- `DATABASE_URL`: `iam_crm_runtime`, an ordinary login with CRUD grants,
  `NOSUPERUSER`, `NOBYPASSRLS`, `NOCREATEDB` and `NOCREATEROLE`. It does not own
  protected tables. Ordinary API code uses only this URL.
- No additional generic bypass role is created. Tenant ADMIN and Platform Admin
  never receive PostgreSQL bypass authority. Full backups and migrations use the
  explicitly controlled owner credential outside ordinary HTTP handling.

Run `scripts/rls-runtime-role.sql` as the migration owner with a secret supplied
through psql, never a command committed to source control:

```text
psql "$MIGRATION_DATABASE_URL" --set=runtime_password='<secret>' --file scripts/rls-runtime-role.sql
```

The script is safely repeatable for the fixed role name. Role provisioning is an
operator/infrastructure step, not a Prisma migration: role names and CREATEROLE
authority vary by environment. Real `.env` and `.env.docker` files remain
untouched.

## Transaction boundary and policy

`PrismaService.withTenantTransaction` starts an interactive transaction and
parameterizes `set_config('app.current_organization_id', organizationId, true)`.
The `true` flag makes the setting transaction-local on the same connection used
by the callback. COMMIT and ROLLBACK clear it before Prisma returns the connection
to its pool. Callers must use the supplied `TransactionClient`; setting context
in one transaction and querying through the root client is invalid. Existing
transactions use the single `installTenantContext` primitive. Neither function
accepts a DTO/header/query Tenant value; HTTP paths pass the resolver-created,
actively validated `TenantContext`. The reminder job derives organization
identity from the persisted Meeting selected by the scheduler.

The migration creates four clearly named policies. SELECT and DELETE use
`USING`; INSERT uses `WITH CHECK`; UPDATE uses both. All compare the row's text
`organizationId` to `NULLIF(current_setting(..., true), '')`. Missing or malformed
context matches no valid organization and fails closed without a UUID cast.
`ENABLE` plus `FORCE ROW LEVEL SECURITY` is used. FORCE protects a non-superuser
owner if identities are accidentally converged, while the documented migration
owner/superuser remains an explicit controlled bypass. There is no helper
function, `SECURITY DEFINER`, dynamic SQL, unsafe raw query, PUBLIC execute grant,
or client-controllable kill switch.

Notification API CRUD/count/list operations propagate one transaction client.
Audit records remain after successful notification DB units of work, preserving
existing behavior. The Meeting reminder scheduler retains its advisory-locked
atomic transaction and installs each persisted meeting organization before the
notification write; Meeting and AuditLog are not protected in this canary.
Health checks use platform-neutral connectivity and do not query Notification.
Authentication/Tenant resolution does not query Notification, so there is no
bootstrap cycle.

## Index and performance review

Existing indexes are sufficient: `notifications_organizationId_idx` supports
the policy discriminator and
`notifications_organizationId_recipientId_readAt_archivedAt_createdAt_idx`
supports the hot recipient list. No speculative index was added, so there is no
new write/disk/index-build lock cost. On the six-row restored dataset, a 10,000-
iteration internal count signal measured approximately 85.001 ms with RLS
disabled and 76.584 ms with RLS enabled; the representative list plan measured
0.482 ms and 0.340 ms respectively. Both used sequential scans because the
dataset is tiny. This is only a regression smoke signal and supports no
Production performance conclusion.

## Deployment ordering for accumulated fixes 000083-000087

Discover actual server and target SHAs first. Build the latest image before the
maintenance window. Verify backup and isolated restore, disk/capacity, incoming
migrations, role ownership and all preflights. If Production predates 000083:

1. While old writes are still allowed, run read-only Membership and fix 000086
   preflights with the migration owner.
2. Provision/verify `iam_crm_runtime` separately, but do not switch the old API
   to it.
3. Stop old API writes and keep them stopped through migration/backfill.
4. Use `MIGRATION_DATABASE_URL` for one `prisma migrate deploy`. Fix 000086 adds
   no business-data backfill and Notification ownership predates it; therefore
   fix 000087 policy creation/activation does not create an unsafe pause inside
   the migration chain. The owner-operated tools remain able to bypass the
   newly active Notification policy.
5. Run 000083 Membership dry-run, confirmed backfill and validation. Membership
   backfill must precede the 000084+ runtime.
6. Run fix 000086 preflight, dry-run, confirmed no-op backfill and validation.
   Its validation must succeed before requests reach the final runtime even
   though Notification is the only 000087 canary.
7. Verify RLS policy/role smoke tests using the runtime credential.
8. Start/recreate one final latest API image. Its migration command receives the
   owner URL only for `migrate deploy`; the Node process retains the runtime URL.

Thus all pending migrations may run in one owner-operated deploy after the
preflights and write stop; no operator pause is required between 000086 and
000087. One prebuilt final image and one final API recreation are sufficient.
The latest image contains the 000083/000086 operator tools. Never start the new
runtime before their required validations. Never start an old pre-000087 image
under `iam_crm_runtime` after RLS activation because it does not install the DB
Tenant context.

## Rollback and kill switch

Application rollback to a pre-000087 image is safe only if Notification RLS is
first disabled by the database owner or the old image continues using its
reviewed owner credential during a short rollback window. The latter removes
the DB defense layer and is not a steady state. Do not expose a switch over HTTP.

The non-destructive operator kill switch is
`scripts/rls-notifications-disable.sql`. It only disables enforcement; it drops
no policy/table and changes no Tenant ownership or row. Fix 000085 application
scope remains active. After correction, run
`scripts/rls-notifications-enable.sql` and repeat role/no-context/Tenant A/B
smoke tests. On the isolated restore, disable exposed all six rows to the test
runtime role, re-enable restored fail-closed zero-row no-context behavior, and
the owner count remained six before and after. Database restore is not a routine
RLS or application rollback.

Rollback to pre-000086 remains governed by fix 000086's composite Team-code
boundary and becomes unsafe once cross-Tenant duplicate Team codes exist.
Rollback to pre-000084 additionally has the documented session/default-Tenant
limitations. No data restore, `_prisma_migrations` edit or `migrate resolve` is
part of this procedure.

## Backup and deferred expansion

Full logical backup must use the controlled migration/owner identity; using
`iam_crm_runtime` would intentionally dump only rows visible to its active
context (or none). Restore similarly uses an isolated owner identity. Do not put
owner credentials in application logs or ordinary request configuration.

Expansion to other Tenant-owned tables requires a later numbered fix with its
own ownership validation, service/job transaction propagation, role tests,
representative benchmark and rollback evidence. Application scope remains
required whether RLS is enabled or temporarily disabled.
